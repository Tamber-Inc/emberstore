emberstore binary format

MIB1 documents and MIBJ journals · code in emberstore emberstore/Binary (jp/binary working tree), on Miro jamierpond/Miro@8a5f64a8 (jp/reflector-hooks) · 2026-11-11

1. What it is

Saving a Miro-reflected struct as JSON is slow and big, and changing one entry of a large map meant rewriting the whole JSON file. emberstore now has a binary encoding (emberstore::toBinary / fromBinary, in emberstore/Binary) that works on any type that already has a MIRO_REFLECT, no schema file or code generator. It lives in emberstore, not Miro: Miro only carries the format-agnostic hooks it is built on (Reflector::visitPacked(), range-checked number loading, missing containers keeping their defaults). emberstore uses its append-only journal form so a single-entry write adds a small frame to the end of the file instead of rewriting it.

2. How the format works

Every dump below came from a throwaway program built before the code moved from Miro to emberstore/Binary; the move changed only namespaces and include paths, not the bytes written. Bytes are hex; the first 8 bytes of every document are the header.

Document layout

file     := "MIB1" | u32 keyTableOffset | value | keyTable
keyTable := varint keyCount | { varint length | bytes }*
value    := tag byte | payload

Every value starts with a one-byte tag (0 Null, 1 False, 2 True, 3 Int, 4 Double, 5 Float32, 6 String, 7 Object, 8 Map, 9 Array, 10 PackedFloat, 11 PackedDouble, 12 PackedInt32, 13 PackedInt64). Object field names are not written inline: each distinct name is stored once in a key table at the end of the file and fields refer to it by a varint index. Every container carries its byte size up front, so a reader can skip it without parsing it.

Fixed sizes (header offset, container sizes, counts, floats) are little-endian on every host. Each field is built byte by byte with shifts, and whole packed arrays are copied in one go only when the host is little-endian too, so a big-endian machine writes and reads the same bytes. All sizes are u32, so a single document or container is capped at 4 GiB.

Fields wrapped in Omittable<T> are dropped entirely, key and all, when absent; plain std::optional writes a Null.

Fields are identified by name, not position

Fields are tagged, and the tag is the field's name (via the key table), not a number. Field order in the file doesn't matter: the reader keeps a cursor so reading in written order is one step per field, and falls back to scanning when the order differs. Results from the dump program:

Schema changeWhat happened
Field added (old file, new struct)Loads; the new field keeps its default (id=7 name=seven extra=1).
Field removed (new file, old struct)Loads; the unknown field is ignored (id=8 name=eight).
Field renamedValue is lost silently; the field keeps its default unless the struct's own reflect() reads the old name.
Field type changed (int → string)The field keeps its default (id=unchanged), and fromBinary returns a BinaryLoadReport listing it: field path id, stored Number, expected String. Loads still never throw.
Enumerator or variant type renamedBreaks old data: both are stored by name (enum "Blue", variant key "int").

The format is self-describing: every value has a type tag and every field its name, so a reader with no struct definition can walk a file (that is what Binary::View does). What it doesn't record is the C++ type: int vs int64, float vs double all collapse to Int / Float32 / Double.

Random access without decoding

Binary::Document + View let you read doc["tracks"][7]["title"] by skipping siblings via their size prefixes. Opening a Document still reads the whole key table into a hash map, and indexing into a non-packed array is O(index). Data is unaligned, so this is "read in place", not Cap'n Proto-style "cast the bytes to a struct".

3. emberstore's journal

Problem: a Collection is one file holding a whole map; with JSON, every insert rewrote the file (3.2 s for 2000 inserts, below). Now a binary collection appends one frame per insert or delete and only rewrites the file once the appended tail has grown as large as the base.

journal := "MIBJ" | u32 baseSize | baseDoc (a full MIB1 file) | frame*
frame   := u8 kind (1 set, 2 remove) | u32 payloadSize | payload | u32 fnv1a(payload)
payload := varint keyLength | key | [valueDoc, a full MIB1 file, for set]

Real bytes, base {a:1}, then set b=2, then remove a:

4d 49 42 4a 12 00 00 00 | 4d 49 42 31 11 00 00 00 08 04 00 00 00 01 61 03 02 00     MIBJ, base = {a:1}
01 0d 00 00 00 | 01 62 4d 49 42 31 0a 00 00 00 03 04 00 | c4 0f c4 35             set "b" = 2
02 02 00 00 00 | 01 61 | 17 b6 74 4c                                              remove "a"
replayed → {b:2}
  • Checksum: 32-bit FNV-1a over the payload only. The kind byte and length aren't covered by it; a flipped kind (set ↔ remove) passes the check. FNV-1a catches torn writes fine but is weaker than a CRC against real corruption.
  • Torn writes: the reader validates frames in order and stops at the first one whose length runs past the end of the file (cutting the last byte above: truncated=1, frames=1, result a=1 b=2, the remove is lost). emberstore marks the journal damaged and the next write compacts, which rewrites the file cleanly. A frame whose length still fits the file but whose kind, checksum or key is corrupt is skipped, and the frames after it still load; JournalInfo::skippedFrameCount and the load report count it. emberstore doesn't yet compact on a skipped frame, only on a torn tail.
  • Compaction: an append goes ahead while tailBytes + frame ≤ max(baseBytes, 4096); otherwise the whole current map is written as a fresh journal via temp file + rename (fsync'd when Durable). So the file is at most about twice its compacted size.
  • Frame size: each set frame embeds a complete MIB1 document, header and key table included, so every frame repeats the struct's field names. That's why one "nested" entry frame is 1407 bytes.
  • Appends go through a persistent file handle, one write() per frame (POSIX); Windows reopens the file per append.
  • Binary::View refuses journals (it would miss the frames); only fromBinary into a std::map<std::string, V> replays them.

Rows other than MIB1's describe those formats' documented designs; none of them were benchmarked here.

Where MIB1 wins: no schema file and no codegen; existing reflected types gain a binary form for free; arrays of records pay for field names once, unlike MessagePack/CBOR; numeric vectors are packed (embeddings are 4.5× smaller than JSON and encode ~140× faster); and the journal gives cheap single-entry appends with torn-tail recovery.

Where it's weaker: renames need care (a rename loses the value silently unless reflect() migrates it by hand); per-value overhead is high next to protobuf (5 bytes per object header, 9 per array, a tag byte per value), so small flat records end up barely smaller than JSON (nested shape: 1.13×; a single settings struct is larger than its JSON, 113 vs 110 bytes); no real zero-copy; 4 GiB limits; only one implementation (C++), so no other language can read it today.

Is it a fair fight?

  • fsync is like-for-like, but neither side is truly durable on macOS. emberstore calls plain fsync() (AtomicFile.cpp, AppendFile). SQLite's PRAGMA fullfsync defaults to off and the bench doesn't turn it on, so SQLite also calls plain fsync(). On macOS that hands data to the drive but doesn't flush the drive's own cache; only F_FULLFSYNC does. 500 "durable" binary writes in 18.7 ms is 37 µs each, far below a real flash flush. With F_FULLFSYNC on both sides, expect both to slow by orders of magnitude and the gap to narrow (not measured).
  • Reads aren't comparable. emberstore answers from an in-memory cache (one stat + map lookup, no decode); SQLite runs a prepared SELECT and parses the JSON body each time. The read rows measure the cache, not the format; that's why JSON and binary read at the same speed.
  • SQLite stores JSON text as the row body, so its 356 KB matches ember JSON's; it isn't using a binary encoding.
  • Insert timings include emberstore's compactions (whole-file rewrites) as they occur.
